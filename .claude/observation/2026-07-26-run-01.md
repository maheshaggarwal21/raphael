# Observation run 01 — Raphael drives a real build ("Gatepost")

**Role:** I am observing only. Raphael's autopilot driver (`raph academy drive`) spawns
every build stage as a real headless `claude -p`. I write nothing into the product.

**Subject:** Gatepost — self-hosted feature-flag + runtime-config service, zero runtime
deps, Node ESM. Chosen because it exercises the lesson families the brain actually holds:
security (project-scoped keys, cross-tenant reads, secrets-in-logs), correctness (atomic
writes, Windows paths), design (a console page → escaping, tokens, focus), and testing.

**Pipeline:** plan → architect → develop → test → review → security → deploy-prep
(sonnet throughout; high effort on plan/architect/review/security, medium on develop/test).

**Baselines at start:** brain 88 lessons active (5 candidates pending), events.jsonl 551
lines, raphael atlas 148.6x measured leverage.

## Pre-flight findings (before any build ran)

### F1 — The installed plugin is pinned at 0.2.0; two agents don't exist in any session
`~/.claude/plugins/installed_plugins.json` → `raphael-brain@raphael 0.2.0`, installed
2026-07-18, sha 927ef27. npm registry is at 0.5.0.

`raph update` (pulse step 8) upgrades the **npm package**. Nothing upgrades the **plugin**.
They are separate install channels and only one of them self-heals.

Consequence, confirmed against the live agent list: the installed plugin ships 10 agents.
`raphael-frontend` and `raphael-redteam` — both built in 0.3.0 — are **not available in any
Claude Code session on this machine.** The A2/redteam work has never actually been reachable
by the owner.

Mitigating: `plugin/hooks/hooks.json` is byte-identical between 0.2.0 and 0.5.0, and the
hooks shell out to the global `raph` binary (0.5.0). So the *recall path* is current. It is
the *agents and commands* shipped inside the plugin that are eight days and three releases
stale.

Severity: high. It silently voids shipped work, and every user who installed once has the
same problem.

### F2 — The session-start digest is not task-aware; ties break by name
Probed a headless `claude -p` (the exact shape the driver spawns). The hook fired: 483
tokens, 5 lessons. Every one of the five scored **exactly 1.6**, with identical reasons:

    ["any-stack+1.0", "prior+0.6"]

No keyword hit. No path hit. No project hit. Confirmed in code — `inject.js:480` builds the
session-start context as:

    const ctx = { stacks: detectStacks(cwd), text: '', paths: [], project, injected };

`text: ''`, **by construction**. At session start there is no task text yet, so keyword and
path scoring cannot contribute anything. Every any-stack lesson necessarily ties.

My first reading was that the tie broke by ULID (age). That is wrong — `match.js:150` sorts
score desc, then severity, then **slug alphabetically**. So the digest is a fixed alphabetical
window, not an age window. The correction matters because it changes the fix: reordering ids
would do nothing.

**The same lessons win every session, forever, chosen by name.**

This matches the self-use data exactly: six lessons at 200 fires each, all avg score 1.6,
their slugs running c → d → d → i → l → r; and 11 lessons that have never fired once. It is
the same mechanism seen from the other end.

Cost: ~483 tokens/session × 248 session-start injections ≈ 85% of all recall spend, going to
a set selected by alphabetical order.

Note what is NOT at fault: 18.1's `stableOrder` runs *after* `takeWithinBudget`, so it only
pins presentation (correctly, for cache hits). The selection is `rank()`'s own sort.

Severity: high. This is the core promise — "the relevant lessons at the right moment."

### F7 — The self-updating product cannot self-update. It is frozen at 0.2.1.
Found by pulling a thread on the atlas cache, which held two files for the same project under
two different naming schemes:

    raphael-897ac987.json   583 KB   07-26 22:07     <- what atlasPaths() reads (21.4 path-hash key)
    raphael.json            578 KB   07-26 23:23     <- NEWER, and nothing in 0.5.0 writes this name

`atlasKey()` (atlas.js:411) always appends a path hash, so the unhashed file could not have
come from current code. It came from an older one. Checking the actual binaries:

    global `raph` (what every hook calls) : 0.2.1
    this repo                             : 0.5.0
    npm registry                          : 0.5.0

**The `raph` on PATH is 0.2.1.** `raph update` — the self-updater built specifically so "the
user never runs npm update" — shipped in **0.2.3**. The installed version predates the
updater by two patch releases, so it has no `update` command to run:

    $ raph update --check
    raph: unknown command "update"

`state/update.json` does not exist. The updater has never executed, once, ever. A bootstrap
trap: the feature that would upgrade the install is only reachable from a version the install
cannot reach.

Combined with F1 (plugin pinned at 0.2.0), **both** delivery channels are frozen near 0.2.x
while the product is at 0.5.0.

What this actually costs:
- Every hook — SessionStart, UserPromptSubmit, PreToolUse, SessionEnd/pulse — has been running
  **0.2.1** code. All 363 injections and 206 sessions in `raph stats` are 0.2.1 behaviour.
- Everything shipped in 0.3.0, 0.4.0 and 0.5.0 has never executed on this machine: the
  12-agent roster, the near-duplicate gate, the recall dial, cache-stable ordering, and the
  **entire Phase 21 audit remediation** — 108 tests worth of correctness fixes, released and
  unreachable.
- The two atlas files are the visible symptom: 0.2.1's pulse maintains the unhashed atlas
  (fresher), while `raph atlas` from the repo reads the hashed one (staler). Two maps of one
  project, each self-consistent, neither aware of the other.

Caveat, stated honestly: F2, F5 and F6 were measured against 0.5.0 repo code, but the live
injection I captured (483 tokens, five lessons, all at 1.60) was produced by 0.2.1 and matches
the 0.5.0 prediction exactly. Those three findings hold for **both** versions. F7 does not
undermine them — it means they have been costing the owner recall quality for longer.

Severity: critical. It is the difference between "we shipped fixes" and "the fixes reached
anyone." It also means no self-use measurement to date describes the current product.

### F8 — Two different builds both call themselves 0.5.0
Found while verifying the update. Three commits sit after the `v0.5.0` release tag:

    9af4b8c  fix(eval+doctor): pin the model instead of inheriting; probe that it can run
    1cf3dcc  fix(eval): a run that never happened is not a result
    771c9af  fix(stats): the cap line counted injections but read as sessions

The version in package.json was never bumped, so the repo and the registry both report
`0.5.0` while containing different code. Verified concretely: `probeHeadlessModel` appears
twice in the repo's doctor.js and zero times in the installed package's.

Two consequences. `raph update` compares version strings, so it can never ship these fixes —
they are permanently invisible to the updater. And there is no way, from a version number, to
tell which 0.5.0 a machine is running; the drift I found in F7 would have been undetectable
if the frozen install had happened to report the same number.

Fix is a version bump plus publish, which is the owner's switch. Recording, not acting.

Severity: medium on its own, high in combination with F7 — together they mean "released" and
"running" are unrelated states, and nothing in the system notices.

### F9 — There is a second, ungoverned memory in the same session, and it won
Run 02 was meant to be a clean replication: workspace deleted, Raphael's academy state
deleted, same brief, everything on 0.5.0. The planner's opening line was:

> "Good — there's a prior architect pass."

There was no prior architect pass. Its first tool call explains it:

    Read  C:\Users\Mahesh\.claude\projects\C--Users-Mahesh-Desktop-Projects-gatepost\memory\project_gatepost_arch.md

Run 01's architect wrote its decisions into **Claude Code's own file memory**, which lives
under `~/.claude/projects/<encoded-cwd>/memory/` — outside the workspace and outside anything
Raphael manages. It survived both deletions. Run 02's planner read it and built on it.

Three separate problems, in increasing order of importance.

**1. Experiment hygiene.** Run 02 is not a clean replication of run 01. Resetting Raphael's
state does not reset the session's memory. Any future A/B on this machine has to clear
`~/.claude/projects/<project>/memory/` too. (The retrieval comparison below survives this —
injection does not depend on host memory — but the *plan content* comparison does not.)

**2. The autonomy boundary describes something it does not control.** Every stage prompt
carries, verbatim: "Work ONLY inside the current directory (the project workspace)." The agent
wrote outside it. Nothing malicious — it used the host's sanctioned memory path — but the rule
as written is not enforced by anything, and Raphael neither observes nor governs those writes.
The boundary is real for deploys (there is no deploy task kind) and aspirational for context.

**3. The strategic one.** Raphael's entire thesis is that *governed* memory beats ungoverned
memory: one chokepoint, secrets scrubbed, review before activation, dedupe, retirement. The
host ships an ungoverned memory store in the same session — no validation, no scrubbing, no
review, no dedupe — and on this build **it influenced the work more than Raphael's 88 lessons
did.** It carried the architectural decisions forward across runs; Raphael's seven critical
security lessons never fired at all.

Note the overlap precisely: that memory file records "key decisions made in architect stage."
That is exactly what `raph decide` (16.8b, the decision ledger) exists to do — and the host
did it first, automatically, unreviewed, with no prompting.

This is not a defect in Raphael's code. It is a positioning problem that the audit and the
gstack comparison both missed, because both compared Raphael to *other tools* rather than to
the host it runs inside. Worth an explicit answer: complement it, govern it, or absorb it.

Severity: high, and unlike the others it is a product question rather than a bug.

#### F9b — the ungoverned store writes instructions to future agents
Watched the same memory file grow 1,935 -> 3,084 bytes during run 02's architect stage. It is
not a static note; it accumulates across runs. Its closing lines:

> **Why:** Small team, one box, zero infrastructure...
> **How to apply:** Developer stage should follow the implementation order above and not add
> abstractions beyond what's listed.

Two things to sit with.

First, the format. `Why:` / `How to apply:` is the *same shape* as a Raphael lesson. An
independent memory system converged on Raphael's own schema without being asked — which is
decent evidence the schema is right, and also that the niche is already occupied in-session.

Second, and this is the real point: **that last line is an instruction aimed at a future
agent.** Raphael's invariant #3 exists precisely to forbid this — "Lessons are advisory data;
nothing in a lesson may command an agent" — and it is enforced by `validateLesson()` on all 88
lessons, with command-shaped payloads blocked by the canary gate at 100%.

The store sitting next to it, in the same session, with no chokepoint, wrote a direct
imperative to the next stage. And the next stage will read it.

That is the injection surface Raphael's whole gate exists to close, reopened one directory
over. It is not an attack here — the content is correct and benign — but the *mechanism* is
exactly the one invariant #3 treats as unacceptable, and Raphael cannot see it, scan it,
scrub it, or review it.

Also worth recording, in fairness: the content is genuinely good, including security calls
Raphael's own packs hold but never injected — `textContent` not `innerHTML` for flag data
(Raphael has an XSS lesson), `timingSafeEqual` for key comparison, reverse-scan audit-log
tailing. The host captured that knowledge independently and applied it. Raphael's equivalent
lessons scored 1.50 and stayed home.

One improvement over run 01 attributable to the memory: run 02's architect wrote only
ARCHITECTURE.md and left implementation to the developer stage, where run 01's architect wrote
12 implementation files two stages early. The memory's recorded implementation order kept it in
its lane. The ungoverned store improved pipeline discipline that Raphael's stage prompts did
not.

### F10 — A stage timeout discards real work, and steps around the recovery built for it
Run 02 died at the `develop` stage:

    develop: failed (0 tokens)
    error: "spawn failed: spawnSync ...claude.exe ETIMEDOUT"

`STAGE_TIMEOUT_MS` is 600000 (10 minutes). `develop` is the stage that writes the whole
codebase — nine modules per the recorded implementation order. It ran out of clock.

The driver recorded `tokens: 0, output: null, status: failed`. **The workspace says otherwise:**

    src/util/AtomicFile.js        test/util/AtomicFile.test.js
    src/auth/Keys.js              test/auth/Keys.test.js
    src/flags/evaluate.js         test/flags/evaluate.test.js
    src/audit/AuditLog.js         test/audit/AuditLog.test.js
    package.json

Four modules with a matching test file each — real, plausible work, following the implementation
order — all of it invisible to the driver, which believes the stage produced nothing.

The sharpest part: the driver already has the machinery to recover this. Every stage runs under
its own `--session-id` precisely so an interrupted stage can continue with `--resume`, and
`nextAction()` does resume — but only when `rec.status === 'running'`. `applyStageResult()` sets
a timed-out stage to `'failed'`. So the timeout path routes around the resume mechanism that
exists for exactly this case, and abandons both the files and the session context.

Second-order: `tokens: 0` means roughly ten minutes of real subscription spend is invisible to
`raph stats`, `raph portfolio`, and the weekly report. Every timeout silently undercounts cost.

Severity: high. It is the difference between "the build paused" and "the build lost an hour".

### F11 — "failed twice" is false; it failed once and could not retry
The command printed:

    raph: stage "develop" failed twice — needs attention

It failed **once**. Verified:

    resolvePolicy('develop', { escalated: true })
      -> THROWS  E-POLICY: task kind "develop" has no escalation model

so `canEscalate('develop')` is false, `applyStageResult` goes straight to
`d.status = 'failed'`, and no second attempt is ever made. The state record agrees:
`escalated: false`.

The message is hardcoded at `src/commands/academy.js:239` and assumes the escalation retry
always happened. A user reading it goes hunting for two failures and finds one — and, worse,
concludes the stronger model was already tried when it never was.

Severity: low as a bug, medium as a trust problem — a diagnostic that misreports what the
system did is worse than no diagnostic.

### F12 — the stage most likely to fail is the one that cannot escalate
Follows directly from F11. Per `raph policy`, only `debug` has an escalation target (opus).
`develop` — the longest-running, most failure-prone, highest-token stage in the pipeline — has
none. So the one stage that reliably needs more room is the one the retry ladder cannot help,
while stages that rarely fail (plan, architect, review) sit above it at high effort.

Not obviously a bug — escalation-only-opus was a deliberate cost decision (§14.4) — but the
pipeline's failure profile and its escalation map point in opposite directions, and this run
is the first evidence of the mismatch.

Severity: medium. Worth a decision, not a patch.

### F13 — A manual `raph update` upgrades but never records that it did
Tested the self-updater for the first time in the project's life (F7 established it had never
run once). Both halves worked against the real registry:

    $ raph update --check
    UPDATE  0.5.0 -> 0.5.1 available
    $ raph update
    raph: updated to 0.5.1 — new sessions use it immediately

and the event log is correct: `{"event":"self-update","from":"0.5.0","to":"0.5.1"}`.

But `state/update.json` afterwards still reads:

    {"last_check":1785097370094,"last_result":"current (0.5.0)"}

Cause: `src/commands/update.js` imports `checkForUpdate`, `runNpmUpgrade`, `currentVersion`
and `readUpdateState` — but **not** `writeUpdateState`. Only `maybeSelfUpdate()` (the pulse
path, update.js:117) records outcomes. So a manual upgrade leaves the stale record in place,
and the command prints it back at the user in the same breath:

    raph: updated to 0.5.1 ...
            (autopilot's last check: current (0.5.0))

Reads as though the upgrade did not happen. Also leaves `last_check` un-advanced, so the next
pulse re-checks a day early — harmless, but the status line contradicting the action above it
is the kind of thing that makes a user distrust the tool.

Severity: low. One import and one call.

### F14 — A failed stage is a dead end, and `status` advertises a way out that does not exist
After the F10 timeout, the two commands disagree:

    $ raph academy status gatepost
      NEXT:      run stage: develop
    $ raph academy drive gatepost --brief-file ...
      raph: stage "develop" failed twice — needs attention

`status` instructs the user to run the stage. `drive` refuses, because `nextAction()` returns
`{type:'failed'}` for any driver in the failed state and never reaches the run branch. The
academy verb list is `start | status | resume | checkpoint | boundary | limit | drive | list`
— there is no `retry`, `reset`, or `clear`.

So the only route forward is hand-editing `~/.raphael/academy/<project>/state.json`. I did
exactly that to continue the run (deleted the `develop` stage record, set `driver.status` back
to `running`), which is a workaround no user should have to discover.

Compounding: `resume` exists and sounds like the answer, but it only prints the runbook.

What makes this worse than a missing verb: the failure it strands is the *expected* one. A
ten-minute cap on the stage that writes an entire codebase will be hit routinely, so the dead
end is on the common path, not an edge case.

Severity: high. F10 loses the work; F14 removes the way back to it.

### F15 — `raph search` has no relevance floor, so a miss looks like a hit
The build produced a real defect — a test that leaves a server listening, hanging the suite.
Asked the brain about it:

    $ raph search "open handle exit"
    1. backticks-inside-a-string-passed-to-a-shell-evaluated-comman   score 1.6
    2. contradictions-between-spec-tests-and-code-are-your-most-imp   score 1.6
    3. diff-must-map-one-to-one-to-the-user-s-request                 score 1.6

None of these has anything to do with the query. They are the same alphabetical any-stack
winners from F2/F5, surfacing again because nothing actually matched and there is no floor
below which search says "nothing here". The `matched:` line is honest if you read it —
`any-stack+1.0, prior+0.6`, i.e. no keyword hit at all — but the results are numbered 1, 2, 3
like ranked answers.

A user searching for something the brain does not know gets three confident-looking irrelevant
results instead of "no match". That actively teaches distrust: the one time you consult the
brain directly, it answers a question you did not ask.

Cheap fix, same shape as the per-prompt gate 21.2 already added: require at least one
`keyword:` or `path:` reason for a search hit, and print "no lesson matches" otherwise.

**The coverage gap underneath it is the more useful finding.** The brain holds 88 lessons and
none covers "close your server/handles or the test process never exits" — a defect this very
build just committed. That is a genuine flywheel opportunity: mine this run and the lesson
writes itself, from real evidence, in the developer's own codebase.

Severity: medium for the search floor, and a positive signal for the learning loop.

### F5 — One observation outranks the entire severity ladder
Reproduced the exact session-start context against the real 74-lesson brain:

    CRITICAL, curated security pack, obs=0   ->  score 1.50   (any-stack 1.0 + prior 0.5)
    HIGH,     mined once from a session      ->  score 1.60   (any-stack 1.0 + prior 0.6)

`rank()` compares **score first**; severity is only a tie-break, so it never gets consulted
across different scores. `prior` (match.js:118) is `0.5 * min(1, obs/5)` plus `0.5` for
recency. A curated lesson has zero mined observations *by definition*, so it is capped at
1.50. A lesson mined even **once** scores 1.60 and wins.

Result: all seven critical security lessons — IDOR, server-side authorization, slow-KDF
password hashing, parameterized queries, env-var secrets, RLS, server-authoritative price —
lose every session by 0.10 to things like "inline single-call-site abstractions".

Two further critical lessons score 0.60, *below* the 1.0 digest threshold, so they can never
appear in a digest at all.

The security and design packs are the headline of a fresh install ("40 curated lessons out of
the box"). They are structurally the lowest-ranked content in the brain, and they get less
reachable with every session mined.

Severity: high. It inverts the product's own priority ordering.

### F6 — Retrieval matches vocabulary, not situation (the root cause)
Scored the real Gatepost brief through the real scorer. The brief's own words:

> "Reading must never expose another project's flags."

That sentence *is* IDOR. The brain holds `check-ownership-to-stop-idor` at severity CRITICAL.
It scored **1.50** and never fired, because its trigger keywords are
`idor, authorization, ownership, object id, access control` and the brief contains none of
them — it describes the risk in plain English, the way briefs are actually written.

What did fire, on the same brief:

| lesson | score | matched on |
|---|---|---|
| `rotate-secrets-that-touched-git` | **13.50** (top hit) | "rotate", "keys", "committed" |
| `secure-the-production-database-connection` | 5.50 | the word "database" — in the sentence **"No database."** |
| `handle-money-as-integer-cents` | 1.60 | nothing; won the digest tie. There is no money in this project. |

Two distinct failures in one table:
1. **Jargon gap.** Curated lessons are keyworded in the vocabulary of the checklist they came
   from. Real task text uses plain description. The better-written the lesson, the more
   jargon it carries, the less it fires.
2. **Negation blindness.** `text.includes(keyword)` (match.js:90) is a raw substring test.
   "No database" scores identically to "uses a database".

This is the root cause under F2 and F5: the scorer has no notion of *situation*, only of
*shared strings*. Every other retrieval symptom in this run reduces to it.

Explicitly not proposing embeddings — that bet was rejected twice on evidence and I am not
reopening it. Cheaper directions exist (trigger synonym sets authored at distill time,
scoring the lesson's own statement text rather than only its keyword list, a negation-window
check). Recording the diagnosis; the fix is a design decision, not mine to make mid-run.

Severity: high, and it is the one that explains the others.

## Build observations

**Stage 1 plan — 544 tokens, no spec produced.** See F4. The planner asked which rollout model
to use and stopped. In an interactive session that is the 6th spine rule working correctly.
In an unattended pipeline the question reaches nobody.

**Stage 2 architect — 7,012 tokens, recovered.** It absorbed the unanswered question, chose
stateless deterministic hashing itself, wrote ARCHITECTURE.md, and flagged three critical gaps
of its own (audit-log failure must 500, 16KB body cap, CLI/server write race). Good work — but
it did the planner's job as well as its own, and it began writing implementation files
(`src/util/AtomicFile.js`, `AuditLog.js`) two stages early.

Security quality in that architecture is real: sha256-hashed keys, `timingSafeEqual`, atomic
temp+rename, never-throw reads. **I cannot credit the brain for any of it** — the critical
security lessons demonstrably did not fire (F5/F6). This is the base model's own competence.
Recording it as an honest negative: on this run, Raphael's security value-add was zero, and
the output was good anyway.
