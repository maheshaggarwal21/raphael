# Observation run 07 — full-build, end to end

**The open question this run exists to answer.** `full-build` has shipped
EXPERIMENTAL since 23.5 and has never completed a live run. Its one attempt
(run 06, 2026-07-28) hit the subscription limit at 4 of 11 nodes. It did prove
the loop mechanism fires for real — `critique --changes--> architect` produced
two separate architect visits with their own attempts and token accounting —
but four of its structures have NO live evidence at all:

- the `frontend <-> design-review` loop (the loop the whole phase was built for)
- the `review <-> debug` loop
- the `security --changes--> @owner` edge (invariant #4 enforced structurally)
- `deploy-prep`, and therefore a clean terminal `done`

The gate for removing the experimental flag is a run that FINISHES. Anything
less and the flag stays — removing it on partial evidence would be exactly the
self-reported success this whole phase was designed against.

**Role.** Observing only. I wrote the brief; Raphael's own agents write 100% of
the spec, design, UI, code, tests and reviews. I verify the result myself and
never trust a stage's self-report — the `--verify` gate exists because a `test`
stage once reported "135 total tests" while the suite was red.

**Subject.** "Intervals" — a single-page interval timer.
Brief: `.claude/observation/intervals-brief.md`.
Workspace: `C:/Users/Mahesh/Desktop/Projects/intervals` (own git repo, empty at start).

Chosen deliberately:
- the scheduling logic is a PURE function of (routine, elapsed ms), so I can
  verify it head-lessly without a browser — no self-report needed;
- it has a real UI, which is what gives `frontend` and `design-review` genuine
  work rather than a token pass;
- the brief names six specific edge cases, which is a concrete checklist I can
  check the delivered tests against rather than accepting "tests pass";
- zero deps and no build step, so "it runs" is a fact I can establish.

**Verify command.** `node --test test/` — the owner-supplied claim gate. It runs
after every code-bearing node (frontend, developer, test, debug).

### G1 — The brain measurably changed the deliverable (not just "tokens injected")

`plan` ran with `brain: 5 lesson(s) injected` and produced a 102-line SPEC.md.
Its success-criteria section contains, unprompted by the brief:

> "Body text meets 4.5:1 contrast; focus outlines are visibly present
> (restyled, never removed) so keyboard-only use of build/reorder/run

The brief never mentions contrast, focus outlines or keyboard use. That

This matters because 23.7's whole point was that the driver used to compute
lesson matches and throw them away. This is the first live evidence that
closing that gap changes the *output*, not just the prompt. Recorded as a
positive finding, since the honest failure mode would have been "5 lessons
injected" with no trace of them anywhere downstream.

### F1 — REAL BUG: the compiled index drops `provenance`, so the curated
### confidence floor never applies to any injected lesson

Found by pulling on G1: the driver reported the injected lessons as

```
[0/10] pair-type-deliberately-not-inter-by-default
[0/10] keep-a-visible-keyboard-focus
[0/10] server-is-the-authority-on-price
[2.4/10] contradictions-between-spec-tests-and-code-...
```

`keep-a-visible-keyboard-focus` is a design-pack lesson whose file carries
`provenance.tier: curated`, and `confidence.js` floors curated at 6:

```js
if (tier === 'curated') c = Math.max(c, 6);   // expert floor, resists age
```

It reported 0. Reproduced directly against the real brain:

```
provenance present in index entry?  undefined
tier as index sees it:              undefined
computeConfidence(index entry)   =  0
computeConfidence({tier:'curated'}) = 6
```

**Root cause** (`src/lib/compile.js`, the index-entry projection): the entry is
built field by field — id, slug, title, status, category, severity, scope,
triggers, evidence, injection, counter_indications, file, hash — and
**`provenance` is not among them**. So every consumer reading a lesson through
`loadIndex()` sees `provenance: undefined`, and all three provenance-driven
confidence rules silently no-op: the curated floor (6), the `human_edited`
bump (+1), and the auto/machine probation discount (×0.9).

This is not cosmetic. Confidence is computed from evidence alone, and curated
lessons have `observations: 0, distinct_projects: 0` **by definition** — they
were authored by experts, not mined. So the 40 curated lessons that seed every
fresh install (26 security + 14 design) all report **0/10** through the
injection path.

**Blast radius — verified caller by caller, not assumed:**

| consumer | lesson source | affected? |
|---|---|---|
| `driver.js lessonMatchesFor` | `loadIndex()` | **YES** — every autopilot stage's `<raphael-lessons>` envelope, and the effort router's input |
| `commands/agents-md.js:23` | `loadIndex()` | **YES** — lesson ordering in the generated AGENTS.md, the cross-CLI surface |
| `commands/optimize.js:10` | `readActiveLessons()` | no — reads raw files, provenance intact |
| `commands/lint.js:15` | `readActiveLessons()` | no — so the retire sweep is safe; curated lessons are NOT at risk of being proposed for retirement |

The `preference` floor (5) is unaffected because it keys off `category`, which
the index does carry.

**Why it matters most in the driver:** the envelope literally tells the agent
`(confidence 0/10)` next to an expert-curated security or accessibility rule.
An agent told a lesson is zero-confidence may reasonably discount it — so the
bug actively undermines the highest-quality lessons in the brain, and does it
specifically on the path 23.7 built to make lessons matter.

**Not fixed yet, on purpose.** A driver run is in flight and reads this index;
patching `compile.js` mid-run could perturb the very build I am observing. Fix
+ red-then-green regression test after the run terminates.

### G3 — `critique` did real adversarial work, and its calibration held

The `architect -> critique -> architect` loop fired (architect is now on visit
2, with its own record — the per-visit machinery reproducing run 06's result).
The question that matters is whether critique earned the round trip or was
reflexively contrarian. It earned it.

**Real defects it found:**

1. **A genuine Windows bug.** The design's corruption-recovery path quarantines
   a bad file by renaming it to `routine.corrupt-<ISO>.json`. `toISOString()`
   emits `2026-08-03T12:34:56.789Z` — colons — and NTFS forbids `:` in
   filenames, so the rename throws. Critique's argument for elevating it to
   blocking is the sharp part: the document *claims* Windows-first compliance
   and gets harder Windows details right elsewhere, so "a failure mode its own
   error map marks handled is silently untrue on the target platform."
2. **An arithmetic error.** The per-file LOC table sums to ~2,240 against a
   stated headline of ~1,300 — and the design elsewhere tells the build stage
   that past ~1,700 it is building something unasked-for. So the build stage
   was about to be handed a contract the design's own table contradicts.
3. **A missing algorithm.** `nextBoundaryMs()` has a signature and no
   definition, while `computeState()` gets ~20 lines of pseudocode. Skip is a
   required control, so its correctness rests on an undefined function.

**Calibration held.** It ran four checks that came back **"Supported"** and
said so, rather than only reporting problems. It filed three claims under
"plausible but unverified (flag, don't kill)" — including refusing to treat a
`performance.now()`-across-OS-suspend claim as a defect, since the reasoning
was plausible and the fallback acceptable. It quoted the line it objected to
in each case. That is the confidence-banding + quote-the-line discipline
behaving as designed, under live conditions.

Its DECISIONS section also recorded, unprompted, that it did **not** consult an
outside model because none genuinely independent was available in this
environment — an honest negative rather than a silent omission — and that it
deliberately did not re-litigate scope already settled in SPEC.md.

**Cross-check on Raphael itself:** critique's colon-in-filename bug is a class
Raphael could plausibly share, so I checked. It does not —
`academy.js:56` builds its quarantine name from `Date.now()` (numeric), and the
only two `toISOString()` calls in the codebase write JSON *values*, not paths.
Recorded as a checked negative.

### G4 — a real timeout exercised the recovery ladder, and all four properties held

`architect` visit 2 exceeded its 10-minute budget. Live log:

```
architect: retry (stage exceeded its 10-minute budget and was interrupted
           (work on disk is kept; token cost not captured)) (0 tokens)
node architect (visit 2) [architect]: model=opus effort=high (resuming session)
```

State immediately after, read from the real `state.json`:

```
run spent.tokens: {"value":57775,"complete":false}
architect status: running | session preserved: true
  visit1: tokens=38380 tokensCaptured=true
  visit2: tokens=0     tokensCaptured=false
     attempt class=timeout action=resume
edge_visits: {"plan->architect":1,"architect->critique":1,"critique->architect":1}
visits:      {"plan":1,"architect":2,"critique":1}
```

Four separate designed behaviours, all confirmed under live conditions:

1. **A timeout is an interruption, not a model failure.** `classifyFailure`
   returned `timeout` → action `resume`, so it consumed a timeout attempt
   rather than a `model` one. Had it been misclassified, a non-escalatable
   node would have burned its single escalation on a clock expiry.
2. **Resume, not restart.** `session_id` is preserved and status stayed
   `running`, so the driver reattached with `--resume` and the ~10 minutes of
   opus reasoning already on disk was not thrown away.
3. **Cost honesty propagated all the way up.** Visit 2 recorded
   `tokensCaptured: false`, and the sticky-false marker reached the run total:
   `{"value": 57775, "complete": false}`. The run does not present 57,775 as
   the true cost — which it isn't, because a killed child delivers no usage
   envelope.
4. **A resume is not a traversal** — the subtle one. `visits.architect` stayed
   at **2** and `edge_visits["critique->architect"]` stayed at **1** across the
   timeout. Had the resume incremented either, repeated interruptions would
   silently eat the loop budget and escalate a run whose loop never actually
   ran a second time. This property is documented in `graphrun.js`; this is
   the first time I have seen it hold against a real interruption.

### G5 — the artifact guard fired under the exact conditions that originally broke it

```
artifact ARCHITECTURE.md already written this visit — leaving the agent's own version in place
architect: done (11824 tokens)
```

This is the session-18 regression reproducing its trigger and being caught.
`architect` has Bash but no Write/Edit, so it authors a document by shell
redirection across several calls and then returns a *condensed summary* as its
final chat response. Before the `sinceMs` guard, `persistArtifact()` overwrote
the real file with that summary — destroying verified work.

Verified on disk: ARCHITECTURE.md is **44,846 bytes / 484 lines / 16
headings**, not a summary. Its section list also shows the architect mission's
named methodology surviving into real output:

```
## 7. ERROR & RESCUE MAP
## 8. WHAT ALREADY EXISTS
## 9. Build order (minimal path, each step independently verifiable)
```

Two things worth separating. The guard is doing its job **and** it is doing it
on a *second* visit — which is the harder case, because the file already
existed from visit 1 and the guard has to distinguish "stale from an earlier
visit" (overwrite) from "written by the agent during this attempt" (leave
alone). It got that right.

### G6 — the review loop CONVERGES, and the reviewer verifies fixes rather than re-complaining

This is the property that decides whether a bounded review loop is worth
having. A reviewer that can always find *something* never passes, and the bound
then just converts "unsatisfiable" into "escalated" — which is what happened on
tallyboard (run 06) at the old bound of 2.

Trajectory here: **round 1 → 3 blocking defects. Round 2 → 1.** Narrowing.

Round 2 spent most of its effort *verifying round 1's fixes*, not restating
them, and marked each result explicitly:

- re-summed the whole LOC table by hand (root 85 + public 1365 + server 390 +
  test 460 = 2300) — **"Confirmed, not just trusted."**
- independently re-derived all nine rows of the new `nextBoundaryMs` trace
  table, including the cross-cycle, zero-duration and all-zero-guard
  cases — **"Supported."**
- recomputed a contrast ratio from the WCAG relative-luminance formula by hand:
  L(#FF6B6B)≈0.3284, L(#16191F)≈0.00964, ratio **6.35:1** against a claimed
  6.3:1 — **"real diligence, not a restated assumption."** Note this directly
  closes round 1's own "contrast asserted but unverifiable" flag: the architect
  supplied hex values, and the reviewer checked the arithmetic.
- confirmed the Windows colon fix was applied to the timestamp variable only,
  before path-joining, so the `.json` extension survives.
- read `reviews/critique.md` directly to confirm the architect had not
  misrepresented what round 1 demanded — **"No misattribution."** A check
  against the reviewed party fabricating its own review.

The one remaining blocker is a mechanically-checkable contradiction: the
architecture's FSM omits the `reset`-from-`running`/`paused` transition while
SPEC.md lists reset as a mid-run control in two places. Critique's DECISIONS
names its own uncertainty rather than hiding it:

> "a human might judge this an obvious implementation detail not worth blocking
> on, but the document's stated design philosophy ('explicit state machine, no
> implicit modes') makes the omission a real contract gap, not a triviality."

Two other items were explicitly *downgraded* to "Minor, non-blocking notes"
(the Origin-header guard's coverage, and an LOC delta it could not
independently attribute). A reviewer that only ever escalates does not
downgrade things.

**Bound status:** `critique->architect` at 2 traversals of 5. The bound raise
from 2→5 after tallyboard is doing exactly what it was meant to — that run
escalated here; this one has room to converge.

### F2 — SYSTEMIC: the design loop's cost scales with the artifact's surface area,
### and `architect` on opus produces an artifact larger than the code it describes

Not a bug in the graph engine — a calibration problem in what the pipeline
*asks for*, and the most consequential thing this run has surfaced.

**The numbers.** After 4 architect visits and 3 critique rounds, still at the
design stage with no code written:

```
tokens: 110,452 (complete: false)   wall (summed spawn): 35 min
nodes entered: 7   edge traversals: architect->critique 3, critique->architect 2
```

ARCHITECTURE.md is **44,846 bytes / 484 lines** — for an app whose own spec
budgets **~2,300 LOC**. The design document is roughly the size of the program.

**Why that compounds.** Each critique round found a *real*, mechanically
verifiable defect — I checked all three and none were invented:

- round 1: NTFS colon filename bug, LOC arithmetic error, undefined algorithm
- round 2: FSM omits `reset` from `running`/`paused` vs SPEC listing it twice
- round 3: state matrix says delete "stays build" while `onReset`'s ternary and
  the cold-start rule both use 0-intervals as the `empty` discriminator

Round 3 also *confirmed* round 2's fix landed before finding the new one, and
named the irony itself: "exactly the shape of defect the revision says it fixed
the format to prevent, and it slipped through the same matrix in its very next
row."

So this is not an unsatisfiable reviewer. It is a rigorous reviewer against a
**44KB artifact whose internal consistency surface is larger than one revision
pass can close**. Every round legitimately finds something; the bound then
escalates — correctly, since a human should look — but the run does not reach
the code.

**The honest tension.** The loop is working *as designed* and is still, on
current trajectory, a poor use of the budget: ~110k tokens spent making a
design document self-consistent for a timer app, with 8 nodes still unrun. The
graph engine is not at fault. The calibration is: nothing bounds how large an
`architect` deliverable may be, so an opus/high-effort architect fills the
space available, and the reviewer then has proportionally more to find.

**Candidate remedies (not yet decided — needs the run's ending first):**
1. Give the `architect` node a `criteria` that caps design-document size
   relative to the projected LOC, so the artifact stays proportionate.
2. Have `critique` distinguish "blocks the build" from "the build stage will
   discover this anyway" — an FSM row inconsistency is something `developer`
   and `test` would surface in code far more cheaply than a design round trip.
3. Accept it and move `critique` after `developer` instead of after
   `architect`, so adversarial effort lands on code (verifiable) rather than
   prose (arguable).

Recorded now, decided after the terminal state is known.
