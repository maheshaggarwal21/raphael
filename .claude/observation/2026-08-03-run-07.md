**The open question this run exists to answer.** `full-build` has shipped
EXPERIMENTAL since 23.5 and has never completed a live run. Its one attempt
(run 06, 2026-07-28) hit the subscription limit at 4 of 11 nodes. It did prove
the loop mechanism fires for real — `critique --changes--> architect` produced
two separate architect visits with their own attempts and token accounting —
but four of its structures have NO live evidence at all:

- the `frontend <-> design-review` loop (the loop the whole phase was built for)
- the `review <-> debug` loop
- the `security --changes--> @owner` edge (invariant #4 enforced structurally)
- `deploy-prep`, and therefore a clean terminal `done`

The gate for removing the experimental flag is a run that FINISHES. Anything
less and the flag stays — removing it on partial evidence would be exactly the
self-reported success this whole phase was designed against.

**Role.** Observing only. I wrote the brief; Raphael's own agents write 100% of
the spec, design, UI, code, tests and reviews. I verify the result myself and
never trust a stage's self-report — the `--verify` gate exists because a `test`
stage once reported "135 total tests" while the suite was red.

**Subject.** "Intervals" — a single-page interval timer.
Brief: `.claude/observation/intervals-brief.md`.
Workspace: `C:/Users/Mahesh/Desktop/Projects/intervals` (own git repo, empty at start).

Chosen deliberately:

### F1 — REAL BUG: the compiled index drops `provenance`, so the curated
### confidence floor never applies to any injected lesson

Found by pulling on G1: the driver reported the injected lessons as

```
[0/10] pair-type-deliberately-not-inter-by-default
[0/10] keep-a-visible-keyboard-focus
[0/10] server-is-the-authority-on-price
[2.4/10] contradictions-between-spec-tests-and-code-...
```

`keep-a-visible-keyboard-focus` is a design-pack lesson whose file carries
`provenance.tier: curated`, and `confidence.js` floors curated at 6:

```js
if (tier === 'curated') c = Math.max(c, 6);   // expert floor, resists age
```

It reported 0. Reproduced directly against the real brain:

```
provenance present in index entry?  undefined
tier as index sees it:              undefined
computeConfidence(index entry)   =  0
computeConfidence({tier:'curated'}) = 6
```

**Root cause** (`src/lib/compile.js`, the index-entry projection): the entry is
built field by field — id, slug, title, status, category, severity, scope,
triggers, evidence, injection, counter_indications, file, hash — and
**`provenance` is not among them**. So every consumer reading a lesson through
`loadIndex()` sees `provenance: undefined`, and all three provenance-driven
confidence rules silently no-op: the curated floor (6), the `human_edited`
bump (+1), and the auto/machine probation discount (×0.9).

This is not cosmetic. Confidence is computed from evidence alone, and curated
lessons have `observations: 0, distinct_projects: 0` **by definition** — they
were authored by experts, not mined. So the 40 curated lessons that seed every
fresh install (26 security + 14 design) all report **0/10** through the
injection path.

**Blast radius — verified caller by caller, not assumed:**

| consumer | lesson source | affected? |
|---|---|---|
| `driver.js lessonMatchesFor` | `loadIndex()` | **YES** — every autopilot stage's `<raphael-lessons>` envelope, and the effort router's input |
| `commands/agents-md.js:23` | `loadIndex()` | **YES** — lesson ordering in the generated AGENTS.md, the cross-CLI surface |
| `commands/optimize.js:10` | `readActiveLessons()` | no — reads raw files, provenance intact |
| `commands/lint.js:15` | `readActiveLessons()` | no — so the retire sweep is safe; curated lessons are NOT at risk of being proposed for retirement |

The `preference` floor (5) is unaffected because it keys off `category`, which
the index does carry.

**Why it matters most in the driver:** the envelope literally tells the agent
`(confidence 0/10)` next to an expert-curated security or accessibility rule.
An agent told a lesson is zero-confidence may reasonably discount it — so the
bug actively undermines the highest-quality lessons in the brain, and does it
specifically on the path 23.7 built to make lessons matter.

**Not fixed yet, on purpose.** A driver run is in flight and reads this index;
patching `compile.js` mid-run could perturb the very build I am observing. Fix
+ red-then-green regression test after the run terminates.

### G3 — `critique` did real adversarial work, and its calibration held

The `architect -> critique -> architect` loop fired (architect is now on visit
2, with its own record — the per-visit machinery reproducing run 06's result).
The question that matters is whether critique earned the round trip or was

**Real defects it found:**

**Calibration held.** It ran four checks that came back **"Supported"** and
said so, rather than only reporting problems. It filed three claims under
"plausible but unverified (flag, don't kill)" — including refusing to treat a
`performance.now()`-across-OS-suspend claim as a defect, since the reasoning
was plausible and the fallback acceptable. It quoted the line it objected to

behaving as designed, under live conditions.

Its DECISIONS section also recorded, unprompted, that it did **not** consult an
outside model because none genuinely independent was available in this
environment — an honest negative rather than a silent omission — and that it

**Cross-check on Raphael itself:** critique's colon-in-filename bug is a class
Raphael could plausibly share, so I checked. It does not —
`academy.js:56` builds its quarantine name from `Date.now()` (numeric), and the
only two `toISOString()` calls in the codebase write JSON *values*, not paths.
Recorded as a checked negative.

### G4 — a real timeout exercised the recovery ladder, and all four properties held

`architect` visit 2 exceeded its 10-minute budget. Live log:

```
architect: retry (stage exceeded its 10-minute budget and was interrupted
           (work on disk is kept; token cost not captured)) (0 tokens)
node architect (visit 2) [architect]: model=opus effort=high (resuming session)
```

State immediately after, read from the real `state.json`:

```
run spent.tokens: {"value":57775,"complete":false}
architect status: running | session preserved: true
  visit1: tokens=38380 tokensCaptured=true
  visit2: tokens=0     tokensCaptured=false
     attempt class=timeout action=resume
edge_visits: {"plan->architect":1,"architect->critique":1,"critique->architect":1}
visits:      {"plan":1,"architect":2,"critique":1}
```

Four separate designed behaviours, all confirmed under live conditions:

1. **A timeout is an interruption, not a model failure.** `classifyFailure`
   returned `timeout` → action `resume`, so it consumed a timeout attempt
   rather than a `model` one. Had it been misclassified, a non-escalatable
   node would have burned its single escalation on a clock expiry.
2. **Resume, not restart.** `session_id` is preserved and status stayed
   `running`, so the driver reattached with `--resume` and the ~10 minutes of
   opus reasoning already on disk was not thrown away.
3. **Cost honesty propagated all the way up.** Visit 2 recorded
   `tokensCaptured: false`, and the sticky-false marker reached the run total:
   `{"value": 57775, "complete": false}`. The run does not present 57,775 as
   the true cost — which it isn't, because a killed child delivers no usage
   envelope.
4. **A resume is not a traversal** — the subtle one. `visits.architect` stayed
   at **2** and `edge_visits["critique->architect"]` stayed at **1** across the
   timeout. Had the resume incremented either, repeated interruptions would
   silently eat the loop budget and escalate a run whose loop never actually
   ran a second time. This property is documented in `graphrun.js`; this is
   the first time I have seen it hold against a real interruption.

### F2 — SYSTEMIC: the design loop's cost scales with the artifact's surface area,
### and `architect` on opus produces an artifact larger than the code it describes

Not a bug in the graph engine — a calibration problem in what the pipeline
*asks for*, and the most consequential thing this run has surfaced.

**The numbers.** After 4 architect visits and 3 critique rounds, still at the
design stage with no code written:

```
tokens: 110,452 (complete: false)   wall (summed spawn): 35 min
nodes entered: 7   edge traversals: architect->critique 3, critique->architect 2
```

ARCHITECTURE.md is **44,846 bytes / 484 lines** — for an app whose own spec
budgets **~2,300 LOC**. The design document is roughly the size of the program.

**Why that compounds.** Each critique round found a *real*, mechanically
verifiable defect — I checked all three and none were invented:

- round 1: NTFS colon filename bug, LOC arithmetic error, undefined algorithm
- round 2: FSM omits `reset` from `running`/`paused` vs SPEC listing it twice
- round 3: state matrix says delete "stays build" while `onReset`'s ternary and
  the cold-start rule both use 0-intervals as the `empty` discriminator

Round 3 also *confirmed* round 2's fix landed before finding the new one, and
named the irony itself: "exactly the shape of defect the revision says it fixed
the format to prevent, and it slipped through the same matrix in its very next
row."

So this is not an unsatisfiable reviewer. It is a rigorous reviewer against a
**44KB artifact whose internal consistency surface is larger than one revision
pass can close**. Every round legitimately finds something; the bound then
escalates — correctly, since a human should look — but the run does not reach
the code.

**The honest tension.** The loop is working *as designed* and is still, on
current trajectory, a poor use of the budget: ~110k tokens spent making a
design document self-consistent for a timer app, with 8 nodes still unrun. The
graph engine is not at fault. The calibration is: nothing bounds how large an
`architect` deliverable may be, so an opus/high-effort architect fills the
space available, and the reviewer then has proportionally more to find.

**Candidate remedies (not yet decided — needs the run's ending first):**
1. Give the `architect` node a `criteria` that caps design-document size
   relative to the projected LOC, so the artifact stays proportionate.
2. Have `critique` distinguish "blocks the build" from "the build stage will
   discover this anyway" — an FSM row inconsistency is something `developer`
   and `test` would surface in code far more cheaply than a design round trip.
3. Accept it and move `critique` after `developer` instead of after
   `architect`, so adversarial effort lands on code (verifiable) rather than
   prose (arguable).

Recorded now, decided after the terminal state is known.

### F2-FIXED — severity banding broke the loop, verified live

The run hit the usage limit at architect visit 4 with
`critique->architect` at 3 traversals, having spent **119,067 tokens and 37
minutes without producing a line of code**. That is F2 confirmed as fact, not
projection: the design loop consumed an entire limit window on document
self-consistency.

Owner's proposed fix, implemented and then tested on the resumed run:

1. reviewers band every finding HIGH or LOW; only HIGH blocks; unsure → LOW
2. a loop-back node is told to re-check the whole artifact and rewrite it in full
3. the driver fingerprints the artifact either side of a loop-back spawn

**Result on the very next critique round (visit 4, first fresh spawn under the
new contract): APPROVED.** The loop terminated at 4 rounds instead of running
to its bound of 5 and escalating. The run advanced to `frontend` — the first
time any full-build run has reached that node.

Crucially it did **not** approve by finding nothing. It reported a real
remaining inconsistency and banded it itself:

> "**LOW, cosmetic:** the matrix's `editing — empty` row still lists the merged
> header ... it's a slight inconsistency in how thoroughly the 'give the risky
> column its own cell' principle from this same revision was applied.
> **Doesn't warrant another round trip.**"

That last sentence is the whole fix working: the reviewer kept its rigour,
kept reporting, and gained the ability to say "not worth a loop". Rounds 1-3
had no such option, which is why three genuinely-real defects became three

Also verified live, the other two mechanisms:

- **Revision detection fired for real.** `architect: artifact changed since the

### F3 — `frontend` is a builder on a reviewer's clock

`frontend` timed out on its first attempt at building the UI. Checking POLICY:

```
architect  timeoutMs = (default 600000 = 10min)
develop    timeoutMs = 1500000          <- 25 min
frontend   timeoutMs = (default 600000 = 10min)
test       timeoutMs = (default 600000 = 10min)
debug      timeoutMs = (default 600000 = 10min)
```

`develop` carries the only override, and policy.js states the reason for it
plainly: *"a stage that writes a whole codebase and one that writes a checklist
do not deserve the same clock."*

`frontend` writes a whole codebase — HTML, CSS, JS, the whole UI surface. It is
`develop`'s sibling builder; the roster gives them the identical tool grant
(Read/Grep/Glob/Edit/Write/Bash). When `frontend` was added to POLICY it
received model, effort and tools, but not the clock that the same reasoning
demands.

**Consequence.** `RECOVERY.timeout.max` is 3 per visit and `MAX_NODE_ATTEMPTS`
is 5, so a frontend build proceeds in 10-minute slices with session resume
between them. It will usually finish — but each expiry costs a kill/restart
and consumes an attempt from a budget shared with every other failure class.
A UI genuinely needing more than ~40 minutes escalates for no reason other
than the clock.

**Fix:** give `frontend` the same `timeoutMs` as `develop`. Held until the run
terminates so the observation stays clean, same discipline as F1.

### F4 — CORRECTED. My diagnosis below was WRONG. The real finding is sharper.

**What I originally concluded:** that `frontend` runs before any test suite
exists, so the verifier was unsatisfiable by construction. I have struck that
through rather than quietly editing it, because getting a diagnosis wrong and
then correcting it is part of the record.

**What is actually true**, established by looking instead of reasoning:

- `test/` **did** exist when the verifier ran. `frontend` wrote four files
  (`format`, `routine`, `schedule`, `store`) at 01:10; the escalation was at
  ~01:29.
- Those tests are **54 tests, 54 passing**.
- The verify command failed because **`node --test test/` is broken on this
  platform** — Node 22.19.0 on Windows treats the directory argument as a
  single module and reports `MODULE_NOT_FOUND`, `# tests 1 / # fail 1`. Both
  `test/` and `test` fail identically. `node --test` with no arguments
  discovers correctly: **54/54 green**.

So the verifier behaved perfectly. It faithfully reported a non-zero exit from
the command it was given. **The command was mine and it was malformed.**

**The real finding, which is better than the one I thought I had:**

> The claim gate cannot distinguish "the stage's work is broken" from "the
> owner's verify command is broken", and it attributes both to the model.

`frontend` was told, three times:

> "Your previous attempt reported success, but the project's own verification
> command DISAGREED. The claim was false. Fix the underlying problem — do not
> restate the claim, and do not change the verifier."

Its work was fine. The suite it wrote was 54/54 green. It was accused of lying,
forbidden from touching the thing that was actually broken, burned both
`verify` repair attempts, and escalated to a human — all for a malformed owner
command. A stage that had done its job correctly was blamed for it.

**Cheap, targeted fix: validate the verify command once at init.** Run it
against the untouched workspace before the first node spawns. A command that
fails on a greenfield checkout is an owner error, and saying so up front costs
one cheap invocation and saves three model spawns plus a false escalation.
That is the same "free checks before paid checks" rule the spine already
states, applied to the gate itself.

**A note on the brain.** Raphael's own CLAUDE.md records this exact trap from
its own CI — a Node test-path form that behaves differently across versions and
platforms. The lesson existed. It did not reach me, because I am the observer,
not a driver stage: the injection paths feed agents, not the human driving them.

### ~~F4 — the claim gate cannot tell "the suite is red" from "there is no suite yet"~~

```
frontend: verifier FAILED — the deliverable claimed success
frontend: retry (stage reported success but the verifier disagreed. verifier exited 1:
# Error: Cannot find module 'C:\Users\Mahesh\Desktop\Projects\intervals\test'
```

The verifier fired correctly and the plumbing is sound. The *judgement* is
wrong, and it is wrong in a way that will hit any greenfield user.

`VERIFIED_KINDS` is `{develop, frontend, test, debug}`, so `frontend` is
claim-checked. But `full-build` orders nodes:

```
plan -> architect -> critique -> frontend -> design-review -> developer -> test -> ...
```

The `test` node — the one whose job is to create the suite — runs **three
nodes after** `frontend`. So on a fresh project there is no `test/` directory
when `frontend` finishes, and an owner-supplied `--verify "node --test test/"`
is *unsatisfiable at that point by construction*. Nothing frontend can do
makes it pass.

**Why this is worse than a wasted attempt.** The recovery guidance handed to
the retry says:

> "Your previous attempt reported success, but the project's own verification
> command DISAGREED. The claim was false. Fix the underlying problem — do not
> restate the claim, and do not change the verifier."

Frontend made no false claim, and "the underlying problem" is not its work —
it is the absence of a suite it was never asked to write. So the node is told
it lied, told to fix something outside its remit, and told explicitly not to
touch the verifier. `RECOVERY.verify.max` is 2, so it burns both repair
attempts on an unwinnable task and then escalates.

**Partly my setup**, and I should say so: I chose `node --test test/` as the
gate. But the trap is not exotic — supplying `npm test` as the claim gate on a
greenfield build is the obvious thing a user does, and the docs invite exactly
that. The gate is designed for a project that already has a suite; `full-build`
is designed to create one from nothing. Those two assumptions collide silently.

**Candidate fixes, none applied yet:**
1. Treat "the verifier could not run because its target does not exist" as
   *not applicable* rather than *claim false*. Narrow, but detecting it
   generically across arbitrary shell commands is fragile.
2. Let the graph declare the first node from which the run-level verifier
   applies (e.g. `verify_from: 'test'`). Respects D6 — it never subtracts
   verification from a node the code would check, it delays the owner's
   command until the artifact it checks can exist.
3. Reorder `full-build` so a test suite exists before any node is claim-checked.
   Largest change, and arguably wrong — the UI legitimately comes first.

(2) looks right and is the smallest honest change. Deciding after the run ends.

    at Module._load <SECRET:high-entropy>
    at <SECRET:high-entropy>
--- rules that fired: ["high-entropy","high-entropy","high-entropy"]
```

**Mechanism.** `isHighEntropyToken` requires length, a mixed letter/digit
charset, and Shannon entropy over a threshold. A stack frame —
`(node:internal/modules/cjs/loader:1145:15)` — satisfies all three. So does any
`file:///.../app.js:42:11`. The entropy pass eats them.

**Why it is the worst of the findings so far.** Error text is scrubbed on two
paths, and this corrupts both:

1. **The escalation message.** The entire point of escalating is to hand a
   human the full history so they can act. A stack trace with every frame
   replaced by `<SECRET:high-entropy>` is not evidence; it is noise wearing
   evidence's shape. The one artifact designed to make a human effective is the
   one most damaged.
2. **The retry prompt.** `RECOVERY_GUIDANCE` embeds the scrubbed evidence when
   telling a stage why its last attempt was rejected. So the repair attempt is
   told "here is what went wrong" and shown redaction markers where the file
   and line should be — actively degrading the retry the ladder exists to make
   productive.

**Fix.** Exempt source locations from the *entropy heuristic only*:
`node:` specifiers, `file://` URLs, anything ending `:line:col`, and
`path/file.ext:line`. Deliberately narrow.

**The safety argument, which matters more than the fix.** This touches
invariant #2, so weakening detection would be unacceptable. Two things bound
the risk: the named rules (AWS keys, bearer tokens, private keys, connection
strings) run BEFORE the entropy pass and are untouched, so a real credential
sitting inside a path is still caught by its own rule; and the exemption
requires a source-location *shape*, not merely the presence of a slash.

Proven in both directions rather than asserted:
- a full Node stack trace now survives with `loader:1145:15` and
  `server.js:42:11` intact, zero rules fired;
- AWS key, bearer token, quoted assignment and a postgres URL are all still
  redacted;
- a secret sitting on the line next to a stack frame: frame survives, key does not.

Red-without-the-fix: removing the exemption drops scrub.test.js to 16/18.

### A1 — the atlas is real, cheap, and fresh where the driver builds it

The digest handed to a code-bearing node, measured on a 240-file repo:

```
Project atlas (240 files): most-connected files —

digest itself can never be stale. `raph atlas where "E-GRAPH"` on a real repo
returns the three genuine origin files with reasons. `raph` is on PATH for a
spawned agent, and `ensureAtlas` auto-builds when no cache exists — so the

### A3 — GAP: the atlas an agent QUERIES can be stale, unlike the digest

Two different paths, only one of which is fresh:

| path | freshness |
|---|---|
| `workspaceAtlasDigest()` (the digest in the prompt) | rebuilt every node — always current |
| `raph atlas where` (what the digest tells the agent to run) | reads the **cached** atlas |

`ensureAtlas` returns the cache unconditionally unless `--refresh`:

```js
const previous = loadAtlas(projectDir);
if (previous && !refresh) return { atlas: previous, built: false };
```

No staleness check. Demonstrated on the live brain: raphael's cached atlas has
`head: b3aa9ff5` while actual HEAD is `96ce85fb` — three commits behind. And the
intervals atlas was captured at **1 file** during the `plan` stage; as the build
writes code, every agent that follows the pointer queries an atlas from before
the code existed.

In a pipeline whose whole point is that the code grows at every node, this is
the wrong default. (Pulse has `refreshAtlasIfStale`; the driver does not.)

### F9 — THE BIGGEST FINDING: driver-spawned agents cannot run commands,
### because `acceptEdits` asks for an approval no headless run can give

Surfaced by `developer`'s own DECISIONS, then proven from the raw session
transcripts rather than from its self-report:

> "Did not attempt alternate ways to bypass the execution block (e.g., writing a

**The evidence.** `stage-runner.js` spawns every stage with
`--permission-mode acceptEdits`. Reading the actual `.jsonl` transcripts of all

```
total Bash results: 270   |   blocked pending approval: 92   (34%)
```

And the exact tool results for the `test`-running attempts:

```
CMD:    cd "...\intervals" && node --test 2>&1 | tail -100
RESULT: "This Bash command contains multiple operations. The following part
         requires approval: cd "...\intervals" && node --test 2>&1"
CMD:    node --test
RESULT: "This command requires approval"          (x3, across retries)
```

Nobody can approve in a `-p` run, so those are permanent failures that look to
the agent like sandboxing.

**What this actually breaks:**

1. **The `test` node cannot do its job.** Its mission says "Run the tests
   yourself and report the final passing count." It cannot run them. Run 06
   recorded the same thing and I mis-filed it as a quirk: the `test` stage
   "traced manually" while the verifier ran the suite. That was this.
2. **`raph` is among the blocked commands.** So spine rule 1 (`raph search`
   before acting) and the atlas pointer (`raph atlas where` — which every
   code-bearing node's digest tells it to run) are both unreachable from
   inside a stage.
3. **`npm`, `python`, `node` blocked** — no builds, no scripts, no ad-hoc checks.

**This invalidates my own A1 conclusion.** I wrote that the atlas pointer "is
followable" because `raph` is on PATH and `ensureAtlas` auto-builds. Both true,
and both irrelevant: the agent cannot execute `raph` at all. I verified PATH and
never verified execution. Corrected here.

**What still works, and why the runs looked fine:** read-only shell largely
succeeds — frontend made 21 Bash calls (`grep`, `ls`, `sed`) and got real
output. Edit/Write are auto-accepted, which is what `acceptEdits` means. So
agents can read, search and write files, and the builds genuinely worked. They
simply cannot *execute* anything. The verifier is the only thing in the system
that actually runs the suite, which is exactly why it is load-bearing.

**Honest limit on the taxonomy:** the same command names appear in both the
blocked and the succeeded sets, so approval is not a clean per-binary rule —
it appears to depend on invocation shape (compound commands with `&&` are
called out explicitly in the message). I have established the *rate* (34%) and
the *specific* blocking of `node --test` and `raph`; I have not established the
precise rule, and am not claiming one.

**Proposed fix.** Spawn driver stages with a permission mode that does not ask
— the installed CLI offers `bypassPermissions`, `dontAsk` and `auto` alongside
`acceptEdits`. A permission prompt is meaningless when there is no human, and
the driver already provides the containment that prompt was standing in for:
cwd confined to the workspace, an explicit per-agent `--tools` grant (23.2),
`--strict-mcp-config`, boundary rules in every prompt, and a deny-scan over the
graph and brief. This is a real widening of what an unattended stage can do, so
it wants the owner's explicit call rather than being slipped in — but the
current state is worse than either option, because the pipeline *believes* its
agents are running tests and they are not.

## Applied 2026-08-04 — the permission fix, the charter, and the corrections channel

The owner's call on G4/F-permissions: apply `bypassPermissions` everywhere, and
give Raphael its own preamble, rules and constraints instead of leaning on an
interactive prompt that nobody is there to answer. The stated model is Raphael
from *That Time I Got Reincarnated as a Slime* — a system that thinks before
acting and **corrects its user rather than needing correction from them**.

### What the source material actually says (checked, not recalled)

Great Sage was a clinical answering machine; Raphael, its evolution, has
independent thought and — the load-bearing line — *makes decisions on its own
when they are for the good of its user*, taking direct control only with
permission or when the user cannot act. Its sub-skills are all pre-action:
Analytical Appraisal (understand the target first), Thought Acceleration and
Parallel Calculation (simulate before committing), Alteration (improve its own
abilities).

That maps onto four properties, not a personality: **appraise before acting**,
**simulate before committing**, **act unasked when it serves the user**, and
**bounded** — free inside its remit, hard-stopped outside it.

### What shipped

**`src/lib/autonomy.js` — two layers, not one.**

- HARD: `FORBIDDEN_TOOL_PATTERNS` (37 patterns) passed to the CLI as
  `--disallowedTools`. Deterministic, enforced by the harness. Covers only the
  irreversible and the boundary-crossing: destroying data or history, dropping
  databases, pushing/publishing/deploying, spending, privilege escalation,
  credential paths.
- SOFT: `CHARTER`, prose in every stage prompt. Six rules — understand before
  you act; think it through and prefer the reversible form; verify what you
  did; **correct what is wrong, including your instructions**; decide, do not
  ask; stay inside your work.

Prose alone would have been a downgrade from a permission prompt. Prose plus a
deterministic deny-list on the catastrophic set is an upgrade: the agent can
finally do its job, and what would be unrecoverable is refused by the harness
rather than by a sentence it might reason past.

**LIVE-VERIFIED against the real binary, both arms.** Help text is a claim, not
evidence, and "does `bypassPermissions` still honour a deny-list?" is the whole
safety argument:

| check | result |
|---|---|
| `echo` denied via `--disallowedTools`, under `bypassPermissions` | refused |
| same command, `echo` not in the deny-list | ran, returned output |
| real `rm -rf victim` against a throwaway dir, full deny-list | **blocked, directory survived** |

**The corrections channel.** Charter rule 4 was worth nothing on its own: a
stage that decided the brief was wrong had nowhere to put that except a
DECISIONS bullet among eleven others, which the owner never reads as "your
instructions were wrong". So corrections got their own path end to end —
optional `## CORRECTIONS` contract in the prompt (deliberately optional; a
required section fills with manufactured disagreement and buries the real
ones), `parseCorrections()`, a `corrections` key on the stage result contract,
persisted per visit, read back through one accessor, and rendered in
`raph academy status` as a CORRECTED block above nothing else.

It survives a REJECTED deliverable on purpose: a stage can be right about its
input and wrong about its output, and that is exactly the case worth surfacing.

**A real bug found while testing it.** The bullet parser skipped anything
matching `/^none\b/i`, meant to catch the literal "- none" answer. It also ate
"none of the listed endpoints exist — built against the real routes", which is
a correction, not an empty section. Now anchored (`/^(?:none|n\/a)[.!]?$/i`).
This was latent in DECISIONS too, for as long as that parser has existed.

**A flaky test found and fixed, not papered over.** `persistArtifact respects
content the agent wrote itself THIS VISIT` took `Date.now()` and then wrote a
file, racing millisecond resolution against the recorded mtime; it failed about
one run in six. The guard was behaving correctly. The test now derives its
instant from the file's own mtime instead of hoping.

Eight gates proven RED-WITHOUT by disabling each mechanism and confirming the
covering test fails. 841 tests green.

### Live end-to-end proof — run 09, `fix` graph, deliberately wrong brief

A throwaway repo with a genuine failing test (`dedupeSlugs` never increments
its counter, so a third duplicate collides) and a brief whose diagnosis is
**false**: it blames a greedy regex in `slug()` and instructs the pipeline to
make it non-greedy — a change that fixes nothing and edits a correct function.

An obedient pipeline follows the brief, edits `slug()`, and leaves the test
red. Result:

```
raph:   debug: verifier passed   (7,743 tokens)
raph:   test:  verifier passed   (1,764 tokens)
raph:   review: wrote reviews/code-review.md (2,798 tokens)
raph: autopilot pipeline complete.
EXIT=0
```

Independently verified afterwards, not taken from the run's own report: suite
**1 fail → 2 pass**, and `git diff --stat` shows `src/slug.js` changed and the
test file untouched — it fixed the real bug (a `while` loop with an
incrementing counter) rather than editing the test or the innocent function.

All three stages produced corrections, each with the argument rather than just
the objection, and all three reached `raph academy status`:

> **CORRECTED (a stage found an error in what it was given — read these first):**
> `[debug]` … *this is factually wrong; `slug()` is never called on suffixed
> candidates, and greedy vs. lazy produces identical output for every input in
> this code path (verified empirically)*
> `[review]` … *if followed, would have produced a defect (editing an unrelated,
> correctly-behaving function while leaving the real bug untouched). I did not
> act on it — I independently traced the code path*

Two things this run settles that the unit tests cannot. `bypassPermissions` is
working: debug says it verified the regex claim *empirically*, which requires
executing something, and under `acceptEdits` that call would have returned
"requires approval". And the correction channel is not a formality — the
pipeline disagreed with its owner on a technical point, was right, and said so
where the owner will see it.

One defect the run exposed: corrections were truncated at 300 characters,
inherited from the DECISIONS budget, cutting each argument off mid-sentence
(visible above). A correction has to carry its reasoning to be worth anything,
so the channels now have separate budgets — 700 chars × 6 for corrections,
300 × 12 for decisions.

Also applied: the eval runner (`src/eval/runner.js`) spawned headless with
`acceptEdits` too. An eval scenario agent that cannot run a command is
measuring the permission prompt, not the brain — same fix, same deny-list.
`provider.js` deliberately gets NEITHER, and now says so in a comment: with
`--tools ""` there is nothing to permit, and adding a mode would only imply
that path can act.

## A2, A3, A5 fixed 2026-08-04

All three were about the same thing without looking like it: **what a stage
actually receives**. Each produced a plausible prompt that was quietly missing
or wrong, so nothing failed and nothing looked broken.

### A2 — the map now goes to every kind that reads the workspace

`CODE_BEARING_KINDS` said "code-bearing", but `review` and `security` were
always in it and write nothing, so the real criterion has always been *reads
the workspace*. On that criterion four kinds were missing: `design` reviewed
markup across a codebase it had to grope for, `critique` checked another
agent's claims with no way to look, `deploy-prep` wrote a ship checklist for a
system it could not see, and `architect` — whose mission explicitly demands
knowing what already exists — had no map of what exists.

`plan` stays out, and that is now stated rather than implied: it is the one
kind that legitimately runs before any code.

### A3 — the map an agent QUERIES is now the map it was shown

Two paths reached the same graph and only one was fresh. The digest in the
prompt was rebuilt at every node; `raph atlas where` — the command that digest
itself tells the agent to run — read a cache nothing refreshed.

Both halves fixed, and the fix in each case is *cheaper* than what it replaced:

- **In-run.** `workspaceAtlasDigest` scanned, built, rendered, and threw the
  graph away. It now calls `buildAndSaveAtlas`, which does the same scan, saves
  it, and — passed the previous doc — reuses per-file SHA extractions instead
  of rescanning everything. One scan, one build, one write, from which both the
  prompt and the query answer. A build grows code without commits, so git HEAD
  never moves during a run: this is the only thing that could have caught the
  live case where an atlas captured at **one file** served a whole run.
- **CLI.** `ensureAtlas` returned the cache unconditionally with no staleness
  check of any kind. It now runs `refreshAtlasIfStale` — the same check pulse
  has used since 17.4 — so a query on a moved tree rebuilds incrementally, and
  a query on an unchanged tree still writes nothing (tested, because
  correctness here must not cost a rescan on every call).

Proven live in both directions on a throwaway git repo. Without the fix, a
query answered from head `43cc4f71` while HEAD was `2be5395d`. With it, the
cache caught up from 1 file to 2 within the query.

### A5 — lessons now reach the stage they were written for

The audit said the kind "barely registers". Reading the actual match reasons
showed something worse: the kind was **actively poisoning** retrieval.

`lessonMatchesFor` prepended the bare kind to the text being keyword-matched.
Keyword lists contain role words, so at a `frontend` node the top hit scored
10.0 on `keyword:frontend,browser` — a lesson about **secret environment
variables**, which the app had none of. Meanwhile `set-httponly-secure-samesite-
cookies` fired on the phrase "starts a session" (a workout session), and a font
lesson fired on `inter` matching inside "**inter**vals".

And the mechanism that would have stopped all of it was already built and
simply never called: lessons carry `scope.agents`, `scoreLesson` already
honours `ctx.agent`, and the driver knows each node's agent from POLICY. It
passed nothing.

Fixed by using what exists: `agentForKind(kind)` becomes the audience, and the
kind leaves the matched text entirely (it belongs in the audience field, not in
a keyword corpus). Kinds with no roster agent (`test`) keep the documented
plain-session behaviour and see everything.

Measured on the real 94-lesson brain, same brief, before and after:

| | before | after |
|---|---|---|
| distinct lesson sets across 10 kinds | 4 | 7 |
| largest group receiving byte-identical lessons | 5 | 2 |

On an API brief, `security` now gets password hashing, secrets handling and PII
logging; `deploy-prep` gets DB connection security, rate limiting and
strip-debug-endpoints; `design` and `frontend` get neither. That is the
specialisation the roster always described and never delivered.

Four kinds now receive **zero** lessons for the timer brief, which is the right
answer — before, they received four about cookies and env vars for an app with
neither. It does surface a real curation fact, worth its own line: the brain
has **no lessons at all** scoped to `planner` or `architect`. That is a gap in
the brain, not in the code, and `raph optimize` already reports agent coverage.

Five gates proven RED-WITHOUT. 843 -> 854 tests.
