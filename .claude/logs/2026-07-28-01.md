## 23.1 — the planning layer (SHIPPED, 629 -> 685)

`src/lib/graph.js`, `src/lib/recovery.js`, `test/graph.test.js` (56 tests).

Pure: zero spawns, zero tokens, no clock, no file reads. Everything it can reject, it rejects
before a token is spent.

- `validateGraph()` — all 16 rules; returns a deep-frozen NORMALISED graph carrying
  `escalatable` (resolved per node from POLICY at validate time, because only `develop` and
  `debug` carry an escalation model — 2 of 14 kinds, so a shared recovery table saying
  "model: max 1" is right for 2 and wrong for 12 unless it is resolved in advance) and
  `effectiveVerify`.
- Edges are the ONLY control relation; `inputs` is a pure data selector validated as
  ancestors. Defining topology twice is how the draft's own flagship graph could not pass
  its own validator.
- `verify` is additive-only — a graph may EXTEND verification, never subtract it.
- `check` is required and `check.command` is refused: a shell command in a graph would be a
  new execution channel reachable from a shipped template (which `raph update` replaces
  daily). The only command the driver runs stays the owner's `--verify`, typed on the CLI.
- The boundary deny-scan is action-phrased, not keyword-based, and reuses the brain's own
  `isNegatedAt` — so "Publish the package to npm" is refused while "never deploy the app
  yourself" (the correct criteria for a deploy-prep node) passes.
- `redteam` is refused by its own rule, checked BEFORE the policy-membership rule, so adding
  it to POLICY later cannot silently make it drivable unattended.
- Tarjan SCC is iterative — a 20,000-node chain is a test, so a long graph cannot blow the
  stack.
- `pipelineToGraph()` gives a repeated kind its own node (`develop`, `develop-2`). That
  record — silently overwritten by the pre-graph driver's kind-keyed `d.stages[kind]` — is
  the entire justification for this phase.
- `renderGraph()` prints each node's CONCRETE per-visit budget: classes that cannot apply to
  that node read 0, not the table's default.
- `recovery.js` is a separate module on purpose: commitment 2 ("separated layers") only means
  something if the runner cannot see the recovery table, and 23.4 has to be able to prove it
  does not import it.
- `canEscalate()` moved into `policy.js`; driver.js's private copy deleted (one definition).

### Two real findings, both from writing the tests rather than reading the design

1. **Rule 3's orphan case was dead code.** A non-entry node with no inbound edge is *always*
   also unreachable, so rule 4 caught every case first and the specific diagnosis could never
   fire. Its test could not go red until the check order was fixed.
2. **Rule 6 needs a bound on every intra-SCC edge, both directions of a two-node loop.** "At
   least one bounded edge per SCC" is unsound — one SCC can hold two disjoint cycles — and
   identifying the true back edges needs a DFS tree whose result depends on input order.
   Requiring all of them is sound and order-independent.

Both written back into `docs/graph-engineering-plan.md` so the design and the code agree.

## 23.2 — the tool grant and the frontend kind (SHIPPED, 685 -> 698)

### Live verification first, because the milestone's design depended on the answer

The design said to live-verify `--tools <list>` and to ship a documented fallback if the CLI
rejected it. `claude --help` documents the list form — but help text is a claim, not
evidence, so I ran it.

- **Two arms, deliberately.** A `Read,Grep,Glob` stage asked to write a file could not, and
  replied `NOTOOL`; an otherwise identical `Read,Write` stage wrote it. A one-arm test would
  only have shown the model declining, which proves nothing about enforcement.
- **Then the real argument vector.** The first test used a hand-built vector. `--tools
  <tools...>` is *variadic* and `--session-id` now follows it immediately, so I ran the exact
  output of `buildStageArgs` for a real resolved `design` policy and asserted the echoed
  `session_id` still matched. It did.

Enforced. No fallback needed.

### What shipped

- **`frontend` becomes a POLICY kind** (sonnet, high effort, no escalate — a stronger model is
  not what fixes taste). The governed path could not run the Frontend agent *at all* before
  this: `--pipeline` validates against POLICY, and the roster's frontend slug had no kind. So
  the autopilot built every UI with the general `developer` agent, and the design-reviews-
  frontend loop the owner asked for had no builder to review.
- **`redteam` still has no kind, on purpose** — POLICY membership is exactly what makes an
  agent drivable unattended. `initDriver` now also refuses `DRIVER_FORBIDDEN_KINDS` by name,
  ahead of `resolvePolicy`, so a future POLICY addition cannot silently open that door.
- **The tool grant is explicit.** Policy resolves `tools` *from the roster* for every agent
  kind; `buildStageArgs` emits `--tools <list>`. Before this it emitted `acceptEdits` and no
  `--tools`, so `design`, `critique` and `planner` — read-only in the roster — were writers
  inside the driver. A design agent that can silently fix the code it reviews makes a review
  loop meaningless.
- **Two hardening calls made while implementing.** `buildStageArgs` **fails closed** on a
  missing grant instead of defaulting to permissive — a caller who forgets must not silently
  receive every tool, since that is the exact defect being repaired. And an empty grant emits
  `--tools ""` rather than omitting the flag, because omitting it grants everything.
- **Dead kinds pruned.** `implement`, `refactor` and `qa` were never POLICY kinds, so they
  could never fire — three dead entries implying coverage that did not exist. Both kind sets
  now have ONE definition in `policy.js` (23.1 had briefly duplicated `VERIFIED_KINDS` into
  graph.js — a drift risk I created and closed here), with a test that every member resolves.

## 23.3 — lifting every pre-graph run onto the engine (SHIPPED, 698 -> 721)

Fixtures come from the owner's real `gatepost` and `microcache` states — the only two
authentic pre-graph driver runs that exist, and both happen to be edge cases.

Three of the eight shapes were silent bugs:
- A completed run has `stage` one past the end of its pipeline, so "map stage to the cursor"
  yields `cursor: undefined` for **every** completed run — which is both runs on disk.
- Status `retry` means "the session failed, start fresh at the escalated model", the opposite
  of `running`. The obvious lift would hand a failed session id to `--resume`, which the
  driver explicitly forbids.
- Dropping the `timeouts` / `retry_escalated` scalars resets the retry budget: a stage already
  at two timeouts would get three more spawns, and `develop` carries a 25-minute clock.

**A real false positive, caught by using real data.** The gatepost brief ends "Out of scope:
deploying it, publishing it, …" — which *states* the boundary rather than instructing a
crossing — and the deny-scan rejected the completed run outright. Two fixes: the scan now
understands scope-exclusion phrasing, scoped to the same line *before* the match so it cannot
become a one-line bypass (tested in both directions), and migration skips the scan entirely,
because refusing to LOAD a user's finished run is worse than the risk it covers.

A truncation bug of my own: the first fixture cut the brief to 400 characters, which removed
the very "Out of scope" clause the fixture existed to preserve. Briefs are now kept in full.

## 23.4 + 23.6 — the engine swap (SHIPPED, 721 -> 757)

Commitment 2 is now a fact about the module graph rather than a claim in a comment: the runner
moved to its own module, emits raw observations only, and a test asserts set equality of its
return keys and that the file cannot even see the recovery table. `failureClass` is banned
from it, because the RECOVERY table is keyed by it one-to-one with an action.

Commitment 3's per-class bounds are scoped per **visit**, which also fixed a latent bug — the
old driver set `retry_escalated` permanently, so under a loop a node could never escalate
twice. `MAX_NODE_ATTEMPTS` closes the seam between classes.

Commitment 1 checks three things on resume, not one; the state-vs-graph binding is the one
that can actually drift.

The verdict contract is hardened against echo, and the null-verdict test asserts what did
*not* happen rather than merely that a parse returned null.

Two of my own test bugs surfaced here: a loop harness that kept driving a run which had
already stopped (so the assertion described the wrong escalation), and lock tests that
depended on a file left behind by a previous process.

**Raphael's own pre-commit guard blocked this commit** on a `token = ...` binding holding a
verdict word. It was right to — the pattern is high-value. Renaming was the correct fix;
bypassing the hook or allowlisting the file would have weakened real scanning to satisfy a
naming accident.
